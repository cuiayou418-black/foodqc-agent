🔴 刀刀见血（不解决就不能说"能用"）

P0-1 夜班跨日归属 = 0 处理（最致命）。
你益海嘉里是三班两倒、有夜班。代码里 resolve_report_date 只读传入日期，SQL 采集按"自然日 00:00–23:59"整窗过滤（collectors.py）。一个 23:00 开工、次日 01:30 完工的夜班批次，会被算进"第二天"——可业务上它属于"当班/上一班"的日报。现在完全没有"班次/生产日"概念。

证据：grep shift/班次/夜班 在全部逻辑文件中 0 命中；agents.py:44 resolve_report_date 直接返回传入日期，无任何班次换算。
后果：夜班数据张冠李戴，日报数字从源头就是错的——而你的红线是"错了不误导人"。这属于"根上错"，比界面问题严重十倍。

P0-2 "合格率 100%" 旁边亮 critical 红警"出现不合格"——自相矛盾，撞红线。
qc_daily_config.json:75 那条 batch_fail 预警：级别 critical，标题"出现不合格/异常批次"，触发指标是 abnormal_batch_count。而 abnormal_batch_count 把三类都算进去：①质检超标 ②接近限值 ③仓储环境超限（analysis.py:182 level 判定）。
所以：只要有一个批次只是"接近限值"或"库温超了一点点"，就会亮一条 critical 红警、文案写着"出现不合格"——可实际上一个不合格批次都没有。 你的真实报告（10-13）正是这样：合格率 100%、2 个"异常批次"、同时触发"出现不合格/异常批次"预警。

证据：config 第 75 行 title="出现不合格/异常批次" + metric="abnormal_batch_count"；analysis.py:166-186 显示 near_limit / warehouse 违规也会进入 abnormal_batches 并触发该规则。
后果：同事/主管看到 critical"出现不合格"会以为出了质量事故，跑去看却是虚惊——信任一旦透支，工具就废了。这是对你自己定的红线的直接违反。

P0-3 取数仍靠"手动传 Excel"，真实 MES/LIMS 自动取数 = 0。
SqlDataSource 只能读你电脑上的 qc_source.db 文件；ApiDataSource 是骨架（要公司给接口+token，且无字段映射容错之外的真实联调）。

证据：collectors.py:270 明确：未导入数据时报"请先到网站上传 Excel 或连接公司数据源"。
后果：入职后每天手动导 Excel 再点生成，等于"半自动"。这违背你定的上线门槛第 4 条——"你休假一周它照样能用"。无人值守自动取数才是真上线。

P1-1 无"班次 / 班组 / 产线"维度统计。
analysis.py 的 KPI 偏总量（总体合格率、产量达成率），工厂日报通常要按白班 vs 夜班、班组、产线拆分对比。现在 line 字段采集了但没用于分组统计（grep 仅见"按 line 存，未按 line 算"）。

P1-2 整个 qc_daily 还没提交 git（无云端备份）。
git status 显示 qc_daily/ 全部 untracked——一大块成果只在你本地磁盘。硬盘/目录出事就全没了。README 已收录（36 处提及），但代码本身没进仓库。

P1-3 推送无重试、无送达确认。
alerting.py 的 send() 直接 urlopen/sendmail，异常被外层 catch 打印了事。日报漏发比迟发更危险，却没有重试和"是否已送达"的闭环。

P1-4 业务规则散在代码/配置，同事改不了。
"什么是异常""预警发给谁""阈值多少"分散在 qc_daily_config.json 和代码里。入职后同事想调条规则还得找你改——违背上线门槛"不需要你在旁边解释"。

P2-1 单 token 全权限，无分级。 登录只是"能进/不能进"，没有"查看 vs 导出 vs 配置"分级。真实工厂数据敏感，不能所有人都能导出全量。

P2-2 无移动端/车间平板适配。 日报内联 CSS 离线可用（好），但未确认响应式；同事可能在手机/车间平板上临时看。

P2-3 真实导入路径无回归测试。 selftest 用模拟数据，没覆盖真实 Excel 导入的边界（空表、非法值、缺列、GBK 乱码）。
